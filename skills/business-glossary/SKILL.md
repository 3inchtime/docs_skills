# 解释本系统真正用到的业务词

让新人通过词条理解业务规则，并能找到对应实现。分别说明“行业或业务概念是什么”和“本系统如何表示、计算或使用它”。

## 收集候选词

1. 读取目标仓库的项目规则、业务范围、模块清单与当前代码版本。
2. 从领域实体、表和字段、状态枚举、事件、错误、规则判断、测试场景和产品资料中提取候选词。
3. 记录候选词出现位置。先追踪上下文，再判断词义；类名、英文缩写和数据库字段名只是线索。
4. 合并同义词，保留中英文、缩写和内部叫法作为别名。相同叫法在不同市场或产品中含义不同的，分成明确的词条或作用范围。

## 按业务理解价值筛选

收录行业概念、公司内部业务简称、业务状态，以及在本系统具有特殊含义的普通词。判断标准是：不了解这个词，读者是否会误解业务对象、数量、权益、资格、时间窗口、计算或操作结果。

排除纯技术百科词、仓库没有涉及的行业概念，以及只因网上常见而加入的词。“冻结”“可用”“结算”等普通词若有项目专有规则，应收录并解释其边界。

## 分别核对定义与实现

阅读 [词条与证据规范](references/glossary-contract.md)，按以下顺序完成词条：

1. 查现有产品资料、业务契约、术语约定与规则测试，确定项目语境。
2. 行业正式概念需要外部定义时，优先查对应市场、机构或标准发布方的原始资料，记录适用范围。
3. 阅读实际代码、配置、迁移和调用方，说明本系统采用的单位、状态、计算方式和使用限制。
4. 记录项目实现与行业定义的差异。定义的权威性不能自动证明实现符合该定义。
5. 缺少正式业务意图时，把具体问题列入待确认项；已有代码行为仍可以直接说明。

## 编写每个词条

使用 [词条正文模板](assets/term.template.md)。每条至少包含：

- 标准名称、英文或缩写、别名。
- 一句话业务定义与适用市场、产品或规则范围。
- 本系统实际口径，以及与行业定义的差异。
- 带前提、单位和可核算结果的例子。
- 容易混淆的概念与影响的业务规则。
- 真实模块、实体、字段、事件或代码符号的映射。
- 定义来源、证据状态、核验版本和维护归属。

先给清楚定义，再写边界和例子。已确认的口径直接陈述；待确认项说明缺哪条业务信息，不在每句话里重复“可能、通常、视情况”。

## 保存统一词典数据

默认输出 `glossary.json`，结构为 `{"schema_version": 1, "terms": [...]}`，供全文词典、搜索、页面内短解释和模块反向链接共用。

字段使用：`id`、`name`、`aliases`、`definition`、`scope`、`project_meaning`、`example`、`code_refs`、`sources`、`status`。`code_refs` 保存仓库相对路径与可选符号；`sources` 保存来源标题以及 URL 或仓库相对业务资料路径。详细约定见参考文档。

[词典结构示例](assets/glossary.example.json) 仅用香港 odd lot 与 fractional share 演示语境差异，两个词条均标为 `pending`，没有目标代码映射。不要直接把它们加入与证券无关的仓库。

## 连接正文和维护流程

1. 把完整词典放在交接文档最后一个主要章节，按名称、别名和业务类别提供查找入口。
2. 正文首次出现术语时提供短解释和链接；不要要求新人先读完整词典。
3. 将稳定词条 ID 写入 `docs-map.json` 的 `modules[].terms` 字符串数组，建立词条到模块、业务流程和代码的反向导航。它保存模块关联的词条 ID；`glossary.json` 顶层的 `terms` 数组保存完整词条对象，两者层级与内容不同。
4. 规则、状态、字段单位、产品范围或市场口径改变时，检查对应词条和例子。
5. 记录真实维护归属和核验版本；缺少负责人时写待确认，不能虚构审核人。

## 验收

- 词条与当前仓库相关，包含业务含义；通用技术词仅在有明确业务专有用法时保留。
- 行业定义、项目实现和改进建议可以明确区分。
- 例子的单位、前提、计算结果与对应规则一致。
- `verified` 词条有来源和真实代码映射；`pending` 词条列明具体缺口。
- 新读者能用自己的话解释术语，区分容易混淆的概念，并找到受它影响的流程。

有 `repo-docs-review` 时使用其词典与链接检查，再做业务语义审查。单独执行时按上述条件逐条核对；结构检查通过只说明字段和引用符合约定。

# 写清楚代码行为

## 解释的结构

先说明业务结果，再按顺序解释主体、条件、动作和结果。代码链接用于核验，正文承担解释；不要要求新人从路径列表自行重建流程。

**写法示例（合成报告导出 CLI）。** 调用方传入 11 月 2 日作为起止日。入口先比较两个日期，随后向标准输出写 CSV 表头。读取器逐行交出字典，筛选逻辑把其中的 `date` 转为日期并比较闭区间，输出器只接收命中行的原日期字符串和 `report_id`。因此登记表增加的备注列不会自动出现在 CSV。若需求是导出备注，需同时改变输出表头和每行选取的字段。

把失败放回刚才的执行顺序。若开始日晚于结束日，校验在表头写入前终止。若第一条记录已输出，第二条记录的日期无法解析，调用方会收到表头和第一条记录，进程随后报错。消费输出的一方应结合退出码判断是否完整。仅写“导出失败”会掩盖这两种结果的区别。

在目标仓库选择同样能区分两种结果的输入，给出自己的源码位置与观察。教程与实现说明共用样例时，一处写可复制的操作和观察方法，另一处解释产生该结果的机制。

## 将空话变为调查问题

| 原表述 | 应回答 |
| --- | --- |
| 必要时重试 | 谁执行？什么错误？次数、间隔、终态？ |
| 根据情况配置 | 哪个配置？默认值、覆盖顺序、影响？ |
| 扩展性良好 | 新增规则改哪些位置？怎样验证？ |
| 保证一致性 | 哪个边界和状态，由哪段实现提供什么保障？ |
| 完善异常处理 | 哪个错误遗漏？预期返回或状态？ |
| 提升稳定性 | 当前失败表现、拟改动作、验证依据？ |

## 确定性与缺口

事实直接陈述，来源集中在邻近证据区。默认配置与环境覆盖分开。缺生产配置时写明变量与影响，不扩展成整章模糊说明。

待确认项包含具体问题、已查范围、缺少资料、受影响结论和可确认角色。不影响当前实现说明的历史动机，可作为补充推断或未记录事项。

`critical: false` 仅用于不阻碍当前行为理解的补充信息，不能隐藏关键规则未查清。由审查者核对分类。

## 控制防御性说明的密度

调查可以全面，正文要围绕读者的任务。模板是一组待回答的问题，简单模块可以合并小节，删掉不适用的标题。不要为了填满模板，连续说明不存在数据库、队列、事务、监控和各种恢复机制。

每条限制都要回答：它会改变读者的哪项操作、预期结果或修改决定？例如内存券核销模块需要说明“重启后记录消失，再运行演示会重新创建券”，因为这解释了重复运行的结果；调用方始终传普通字典时，不必展开任意自定义映射的副作用与通用原子性问题。

核心路径先完整讲清，再在对应位置说明会改变结果的边界。将重复的环境限制和核验状态集中到验证记录；正文保留相关链接。已核实的关键失败条件不能为缩短篇幅而删除。

## 三类内容分开

1. 当前行为：代码、配置、测试和观察支持的实现。
2. 历史决策：已有 ADR、PR、issue 或明确确认的动机。
3. 未来建议：拟改动作、需求依据、取舍和验证计划。

不要把建议增加的重试画进当前流程，也不要从实现选择反推真实历史 ADR。

## 开发指南与读者测试

每个主要模块选一项符合现有结构的开发任务，写出入口、规则选择点、数据影响、兼容检查、测试和文档更新位置。已有扩展点直接写，需要新设计则标建议。

通用约定集中维护并链接复用，业务词首次出现给简短解释。让独立读者回答：

- 从哪里开始，何时算完成？
- 哪个条件会终止流程，留下什么状态？
- 哪一步第一次修改数据？
- 新增规则从哪里改，哪些规则不能破坏？
- 用什么命令与输入验证，观察什么结果？
- 业务词在本系统是什么意思，影响哪里？

要求读者指出文档依据。找不到时补正文，不用额外口头解释后判通过。

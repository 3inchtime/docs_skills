## 1. 从入口到结果

以模块清单为覆盖依据。每个模块都应解释一个实际执行或使用过程，跨模块主链路另设页面，并链接回模块细节。

先建立步骤表，再写图：

| 字段 | 应填内容 |
| --- | --- |
| 步骤 ID | 稳定标识，例如 `validate_range` |
| 触发条件 | 什么事件或上一结果使它执行 |
| 执行主体 | 当前代码中的组件或函数 |
| 输入 | 业务字段、状态、配置与单位 |
| 动作 | 一次具体判断、读写或调用 |
| 输出 | 返回、状态变化、事件或副作用 |
| 证据 | 实际文件、符号、配置或测试 |

只从名字推测调用关系不足以确定流程。继续查注册、依赖注入、框架生成代码和开关。仓库外部服务保留为边界参与者，仅说明当前代码可确认的请求契约及响应处理。

“已经接收请求”“已写入任务”“远端已处理”“最终业务已完成”是不同结果。异步链路按实际可观察状态分开标记。

## 2. 节点与条件

- 节点名写“检查可用数量”“创建申请记录”等动作。类名、文件名放辅助标签或证据栏。
- 条件写具体比较、状态或规则。拒绝分支说明发生原因和返回结果。
- 配置相关条件注明配置名和可确认的默认值；实际覆盖值未取得时，单独列出缺口。
- 重试标明执行者、触发错误、总尝试次数或重试次数的口径、间隔和最终失败结果。
- 事务只画实现中存在的边界。远程调用不会因为在同一个服务函数里，就自动加入数据库事务。
- “图没有画某机制”不等于“系统没有某机制”。先说明图的范围，再记录已检查的实现位置。
- 对只包含类型或常量的模块，可画真实的消费、加载或数据转换过程；明确该模块没有独立运行入口。

## 3. 证据字段

所有路径相对目标仓库根目录。下面是字段示意，尖括号内容须在实施时替换；不能当作已完成记录。

```json
{
  "id": "<真实模块ID>",
  "diagrams": [
    {
      "source": "<真实图源路径.mmd>",
      "kind": "flowchart",
      "generated": "<生成SVG路径.svg>",
      "node_ids": ["<与图源一致的节点ID>"]
    }
  ],
  "evidence": [
    {
      "id": "<稳定证据ID>",
      "kind": "source",
      "path": "<真实源码路径>",
      "symbol": "<已读取的符号>",
      "statement": "<该实现直接支持的行为>",
      "status": "verified",
      "method": "read"
    }
  ]
}
```

`kind` 可为 `source`、`test`、`runtime`、`business`。`status` 可为 `verified`、`inferred`、`pending`。`method` 可为 `read`、`executed`、`observed`、`confirmed`。

`verified + read` 表示核对过对应材料，不表示测试运行通过。测试存在并读过，可以记录 `kind: test, method: read`；只有真实执行后才使用 `executed`，同时保留输入、环境、命令和结果记录。运行观察的结论仅适用于记录的环境和输入。

节点的文字解释、输入输出和 `evidence_ids` 可以保存在旁侧元数据中。若 `.mmd` 是拓扑来源，不在说明数据中重新手写边列表。复杂交互若改由结构化模型生成图源，应在项目规则中明确唯一来源。

固定 commit 的代码链接保存“当时的依据”。更新流程仍需检查最新变化，永久链接本身不会维持文档新鲜度。

## 4. 图形类型的边界

### 流程图

用于主步骤与关键分支。保留不同失败出口；过多分支时分成主图、校验子流程和错误处理子流程。图旁文字补足单位、精度、时间窗口等会影响理解的细节。

### 时序图

用于跨模块调用顺序、消息投递、响应和后台处理。标明参与者角色。只有证据支持时才画重试、回调或消息确认；不把“发送成功”写成“消费成功”。

### 状态图

使用真实枚举或持久化值，解释用户可见名称与代码状态的对应。每条迁移写触发事件与前置条件。对没有统一状态机的实现，可以列出分散的状态修改位置，并记录其缺口。

### ER 图

突出影响业务理解的实体关系。区分物理外键、唯一性约束与应用逻辑关联。字段类型、单位或基数没有依据时，先查迁移和模型定义。

### 架构总览

交代系统边界、参与者、应用、任务和存储。按读者需要选 C4 层级，不把每一层都设为强制交付。

## 5. 语义审查

代码审查者逐项复核：

1. 入口注册与适用配置。
2. 主路径顺序与最终完成条件。
3. 主要条件和失败出口。
4. 数据写入、事件与状态的前后关系。
5. 事务、超时、重试、重复执行和恢复的真实范围。
6. 图与正文、词典、契约的口径是否一致。

读者测试只提供图、正文和任务，不提供作者的调查过程。要求读者解释正常输入的结果、一个失败条件以及对应修改位置。读者能说清楚后，仍需审查者核对事实。

# 随代码更新文档

## 维护对象

在仓库保存正文、图源、词条、证据索引与组件。生成 HTML、SVG 和搜索索引时使用选定版本及锁文件。修改维护源后重新构建，不在生成物上做无法复现的手工修正。

写清模块维护、业务口径与站点构建的职责。人选未知可待确认，不能凭空填姓名或审核通过。

## 每次 PR

1. 确认比较 base/head；需要 merge base 时按项目流程取得，工具不猜分支。
2. 调用 `impact_docs.py` 获得候选页面、图和词条。
3. 检查未映射文件、新增/删除模块、动态入口、配置、数据库约束和事件使用方。
4. 重读改变的执行路径，更新陈述、条件边、状态、开发指南和词典。
5. 只对真正复查的项目更新核验状态与日期。
6. 构建图和页面，检查结构；关键规则变化时做语义与针对性读者测试。
7. 在同一 PR 说明文档更新，或具体解释为什么没有改变已描述行为。

“无需更新”要具体到事实，例如只改内部变量名，对外行为和文档中的符号引用都未变化。规则、状态、接口、事件与迁移变化要逐项检查。

## CI 顺序

1. 项目实际的 Markdown/MDX 和类型检查。
2. Mermaid 构建，任一图失败停止，不静默保留旧图。
3. 站点构建与搜索索引。
4. `validate_docs.py --strict` 检查交付映射和引用。
5. 链接、可隔离示例和关键页面浏览器检查。
6. 审阅者核对业务语义与读者答案。

命令按现有项目接线。沿用用户对修改、提交、推送或发布的实际授权，不从“维护文档”自动扩大到外部发布。

`review.*` 是审查记录，严格模式不能证明字段填写诚实。保留执行记录，不能把改状态当完成审查。

## 指纹与证据版本

固定 commit 链接保留原始依据，当前分支链接便于开发，分别标识用途。

hash 变化提示复查；不变也不能证明行为没变。共享配置、依赖版本、数据约束、调用关系与外部契约都可能影响原函数。

不要每次发布自动刷新所有页面的最后核验时间。按真正复查范围更新。

## 当前、历史与未来

当前行为由实现支持；历史动机来自已有 ADR、PR、issue 或明确确认；建议记录问题、方案、代价与验证方式。

新决策替代旧决策时保留历史关系。从代码推断的动机不得冒充既成历史。解释性推断可单独标为 `critical: false`，影响业务结果的缺口不能借此绕过门槛。

## 处理遗漏

修复对应模块和映射，再检查同类入口是否遗漏。记录新人试图完成的任务、缺少的信息和最终补充位置。

局部变化更新受影响内容；核心架构或范围变化时再调查相关整体关系。

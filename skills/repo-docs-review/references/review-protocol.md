# 交接文档审查协议

## 角色与输入

代码审查者读取文档、仓库、配置和核验记录；独立读者只读取文档和接手任务；页面检查者操作实际构建产物。三类结果分别记录。

记录分支、完整 commit、未提交改动、文档路径、模块范围和排除项。固定版本源码链接说明当时依据，不能证明文档对新提交仍成立。

## 模块覆盖

从入口清单反查模块归属，包括路由、RPC、CLI、任务、消费者、回调、订阅和公共模块使用入口。检查新增、动态注册及开关条件。

每模块有主页面、具体执行/数据流程、真实源文件和关键规则证据。简单模块可以短，复杂模块可以拆页；拆页后仍保持明确主线。目录与类关系不能代替业务过程。

## 代码语义核对

### 五项语义检查

从本次审查范围取一条主线，把正文、图和实际代码放在同一输入与配置下核对。全量交接从这条主线扩展到其余约定模块；局部审查只追受影响的交接。下表中的问题可直接形成审查意见。

| 检查什么 | 怎样核验 | 哪种缺口需要修正文档 |
| --- | --- | --- |
| 模块边界 | 从已注册入口查调用或加载关系，核对谁负责决定、谁持有数据、谁依赖结果；读图时说出每条关键箭头的方向和含义。 | 目录被画成独立服务，或两个模块都被写成负责最终写入。 |
| 运行流程 | 固定一个输入，沿真实分支走到完成。检查先后、可选步骤、并行汇合和调用方能观察到的时点。 | “处理后返回”跨过了能改变结果的阶段，或把任务已接收当成已完成。 |
| 数据流 | 选一个影响结果的值，从输出反查每一跳的写入与读取，核对投影、默认值、单位、形状和可见范围。 | 上游有该字段，但接收方只读取摘要；正文却说原值直达下游。 |
| 关键实现 | 找到实际执行的判断、注册、优先级或转换。挑两个能区分规则的输入，比较正文预测与源码或断言。 | 链接能打开，却无法从正文解释为什么同类输入会走向不同结果。 |
| 特殊与失败路径 | 在同一流程改变一个条件，查失败点之前已有的输出、处理者、停止或继续的位置及再次调用的结果。有连续副作用时，另查首次写入后的失败或整体提交保证。 | 文档只讲坏输入可跳过，漏掉写入中断后留下的部分结果；或声称可续跑却缺少恢复条件。 |

**判断标准。** 已查明文档有错，或缺口会误导读者判断职责、结果、故障现场或修改位置时，给出最小反例，相关模块的 `review.code` 记为 `failed`。关键行为尚无足够依据时记为 `pending`，写清缺哪段实现或观察。范围内的关键行为与证据相符可记 `passed`；修订过的结论须先用原反例重查。按该模块实际存在的机制取证。纯计算模块可用返回值、调用顺序与错误传播完成核验。

### 需要深入时

按一次具体执行沿代码检查：

1. 谁能触发，入口是否注册，参数和配置是否改变路径。
2. 校验与业务判断顺序，被拒绝时是否已经产生写入。
3. 状态、金额、数量、时间范围、舍入与唯一性约束。
4. 读取、写入、事务提交、消息发送和外部调用的先后关系。
5. 同步返回与最终完成，实际终态及可观察结果。
6. 错误转换、捕获范围、重试所有者、尝试总次数和间隔来源。
7. 重复调用、重复消费、幂等、清理与补偿是否实际存在。
8. 修改指南中的扩展位置、使用方、测试和兼容要求。

核对图和正文。条件边对应实现，区分异步事件和阻塞调用，状态图只含实际允许的迁移。渲染成功仅证明工具接受图源。

源码、注释和旧文档冲突时，定位并解释当前行为。业务规范与实现不一致时同时记录，不能擅自擦除其中一方。

## 明确表达

| 原句 | 应补充的信息 |
| --- | --- |
| 必要时重试 | 触发错误、负责组件、配置来源、次数及最终失败。 |
| 合理配置 | 配置名、默认值、覆盖顺序和实际影响。 |
| 确保一致性 | 保障对象、范围、机制及可证明的边界。 |
| 具有扩展性 | 新增一种能力的修改点与验证方式。 |
| 后续完善监控 | 当前缺哪个可观察结果，需要哪项改动。 |

事实直接说，推断写依据，未知写缺口及影响，建议写对象、动作和验证方法。保留必要条件，不在每步重复全局免责声明。

检查每条限制是否影响读者的操作、预期结果或修改决定。删除与实际调用无关的理论风险、重复边界和为了填模板而列出的缺失能力；简单模块允许合并小节。读者应先看懂完整业务路径，再遇到会改变该路径的具体条件。

## 独立读者测试

使用新上下文或真实新同事，仅提供可交付文档与任务，允许跟随文档内部链接。不要附作者推理、预期答案、修复方案或源码。

要求读者完成：

- 描述业务输入到最终结果，指出首次写入或状态变化。
- 解释真实失败的条件、停止位置、返回和恢复。
- 根据一个小需求找到修改入口、不变量与验证命令。
- 解释业务专有词、适用语境及代码映射。
- 找到代码基线与已验证/待确认范围。

记录原始答案及引用位置，再由代码审查者核对。找不到、猜测、误解与遗漏都是改写输入。修订后只复测具体问题及直接影响。

出题时保留同一接口，只改变一个会区分两种解释的条件。例如把可选字段从缺省改成显式空值，或把失败从首次写入之前移到之后。预先在审查记录中保存依据与预期，题面只给起始条件和要预测的观察。读者需要用页内证据串起中间步骤；即使碰巧答对终值，缺少关键一步的依据也应记录。修订后换用未公开答案的等价输入，以免把记住上次答案当作理解。

代理独立阅读可暴露解释缺口；真实产品口径仍需业务维护者确认。无法独立测试时记录未完成，作者自查不能冒充独立通过。

## 命令与页面

命令来自任务脚本、CI 或项目资料，只在隔离且已授权的环境执行，记录命令、必要环境、输入、退出码与结果。未执行或依赖阻塞时写具体原因。

对实际文档站检查构建、图渲染、导航、源码链接、业务词及别名搜索、键盘焦点、窄屏、减少动画和打印。必要解释保持静态可读。失败路径的文字、图与结果应一致。

## 完成条件

关键行为和图能回到依据，新人任务有入口和验证方式，页面符合承诺形式。阻断性缺口解决前不要宣称模块完成；不阻断行为理解的推断可标识后保留。

分别记录结构、语义、运行、页面与读者检查。禁止从工具成功退出推导全部业务正确。

# 可视化仓库文档站

先确定内容，再构建页面。让新人能从业务问题进入模块，沿流程理解行为，找到代码与修改方法。

## 接收输入

读取目标仓库规则、已有文档站和实际构建脚本，再接收：

- 已核对的模块清单、模块正文与跨模块业务流程。
- 可维护的图源、生成方式、稳定节点 ID 和图旁说明。
- 业务词典、源码证据和代码基线。
- 未确认事项以及静态阅读、命令执行、运行观察的分别记录。

内容不足时先完成现有内容的可读呈现，并把具体缺口交回调查阶段。发现正文与图冲突时定位原始证据；不要在设计页面时补猜业务机制。

## 选择交付形态

1. 复用已有文档站、设计规范和包管理器。
2. 没有站点时，默认选择 Starlight + Markdown/MDX；先读取官方安装与组件说明，再选择稳定版本并提交 lockfile。
3. 保留 `.mmd` 等可编辑图源，构建生成 SVG。Starlight 的 Mermaid 需要额外集成；本流程默认使用构建时 SVG。
4. 用单文件 HTML 提供便携摘要或局部讲解；完整手册保留多页文档源和构建方式。

开始实施时读取 [站点工作流](references/site-workflow.md)。涉及交互时读取 [组件契约与验收](references/component-contract.md)。

## 先做完整样板

选择已有证据的一个模块，完成以下链路：

1. 把业务职责、一个具体例子、关键规则和失败结果写进 MDX。
2. 从图源生成 SVG，并确认失败会让构建返回非零。
3. 在页面引用图，保留可以搜索与复制的文字步骤。
4. 从步骤链接到真实证据；注明代码基线。
5. 构建站点，检查业务词、别名和代码符号能否被搜索找到。
6. 检查页面布局、键盘操作、窄屏和打印，再扩展到全部模块。

若已有命令不能运行，记录具体命令、环境和错误；继续完成独立可做的内容工作，不把静态检查写成构建成功。

## 组织阅读入口

首页提供“理解系统”“运行一次业务”“完成首次改动”三个入口。完整手册包含模块、跨模块流程、开发任务、运行排障、精确参考与已记录决策，最后提供业务专有名词词典。

让模块页面先回答业务问题，再展示图与实现细节。把源码证据放在相邻区域或折叠区，关键条件、失败结果与业务约束直接可读。保留完整正文，不把交接文档压缩成只有图注的图集。

## 使用可复用组件

可复制以下资源到目标文档工程，再按项目接口适配：

- [flow-reader.js](assets/flow-reader.js)：无框架的逐项说明组件。
- [flow-reader.css](assets/flow-reader.css)：只作用于该组件的样式。
- [flow-reader.example.html](assets/flow-reader.example.html)：显式标注为合成场景的完整 HTML 用法。
- [build_offline.py](scripts/build_offline.py)：把示例或同结构模板中的两个组件资源内联成一个 HTML。

组件保持完整图与全部文字可见，仅突出当前说明项。它不解析 SVG、不高亮 SVG 内节点，也不模拟业务执行；阅读顺序不代表分支路径。

默认让 `.mmd` 保存拓扑，说明元数据通过 `node_id` 关联。需要切换真实业务路径时，从唯一流程模型生成路径数据；不要手工维护第二套分支逻辑。若选 `flow.json` 作拓扑源，则由它生成图源和交互数据。

```bash
python3 <skill-dir>/scripts/build_offline.py --help
python3 <skill-dir>/scripts/build_offline.py --output <output-dir>/flow-reader-demo.html
```

上面导出的是组件示例，不是目标仓库手册。生成真实摘要时用 `--template` 指向已填入真实内容、保留资源标记的模板。

## 保持清楚、可访问和可维护

- 用标题、间距、表格和少量强调建立层级；长路径允许换行，表格和图在容器内滚动。
- 给图提供标题、描述和邻近文字；不要只用颜色区分成功与失败。
- 让关键内容在脚本关闭时可读；让搜索能索引正文中的业务词和条件。
- 给按钮、链接、展开内容保留键盘焦点；尊重减少动态效果的偏好。
- 打印时保留完整静态图、全部步骤与关键证据。
- 把当前事实、实现推断、未确认项和未来建议标识清楚；不要制造完成率、生产指标或已验证徽标。
- 保持文档的访问范围与仓库内容相符，源码引用不包含凭据值。

使用 `visual-explainer` 时，将其限定为已核对内容的局部图解。它的独立 HTML 与渲染流程不能自动成为 Starlight 组件；先适配再验收。

## 分开验收并交付

分别记录以下结果：

1. 内容覆盖：约定模块、流程与词条都有可导航入口。
2. 构建与资源：站点、图和搜索索引成功生成，链接到达正确位置。
3. 页面行为：桌面、窄屏、键盘、脚本关闭与打印检查。
4. 读者理解：读者只凭文档找到流程、失败结果、修改点与验证方式。
5. 事实核对：由代码审查环节核对关键条件、状态和副作用。

使用 `webapp-testing` 或环境已有浏览器工具检查最终页面。浏览器不可用时明确记录未完成的检查；不要把 HTML 解析、截图文件存在或 JavaScript 语法检查当作视觉验收。

交付正文与组件源码、图源、构建配置、已验证的预览命令、实际检查记录和具体待确认项。只有用户授权发布时才发布站点；文档生成授权本身不要求修改生产业务代码。
